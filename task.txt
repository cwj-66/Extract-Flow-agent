# 券商研报摘要 & 群聊分发 Agent —— 任务单

## 一、项目概述

一个面向公司内部员工的工具：上传文档（单份或整个文件夹）→ AI 自动提取结构化信息 → 套用固定飞书 Card v2 模板 → 员工确认/修改 → 自动发送到指定飞书群。

**技术栈：**
- 后端：FastAPI + Pydantic v2 + uvicorn
- 任务队列：默认进程内 `TaskQueue`；可选 Celery + Redis（`USE_CELERY`）
- 存储：`DbTaskStore`（本地 SQLite / Compose Postgres）
- AI 提取层：qwen（DashScope）
- 飞书接入：自定义机器人 Webhook + httpx（Card JSON 2.0）
- 前端：React + TypeScript + Vite（`frontend/`）

**数据清洗管线（已实现）：**
```
PDF → MinerU 解析（版面分析 + 表格→HTML + 公式→LaTeX）
    → 分类器（纯图片判断是图表还是普通图）
    → 清洗（图表→VLM 描述，图片→VLM 描述）
    → 合并为结构化 Markdown
```

已实现的代码位置：`app/cleaners/`；CLI 入口：`main.py`；API 入口：`uvicorn app.api.main:app --reload`。

**部署：**
简单起步：一台云服务器 + Docker Compose，把 FastAPI、Postgres、Redis、前端打包一起跑。

## 二、场景（固定文档类型）

### 核心原则

「任何格式」曾指载体类型；现已收窄为 **仅 PDF**。一种业务 → 一种文档 → 一套固定字段与卡片模板 → 一个群。

**提取字段与卡片布局已固定，不再提供「提取字段配置」CRUD。**

### 固定文档类型

**券商业绩点评研报**（一季报点评 / 年报点评）

- 页数：约 4~6 页
- 特点：结构固定，但关键信息分散在文首、中段、文末
- **处理策略（来自 pineline.txt）：文档不长（几十页内）就整篇喂 LLM，不用 RAG/向量检索**

### 测试文档获取

| 来源 | 说明 |
|------|------|
| [东方财富研报PDF库](https://pdf.dfcfw.com/) | 搜「一季报点评」「年报点评」，免费下载 |
| [巨潮资讯网](http://www.cninfo.com.cn/) | 备选，上市公司法定公告 |

**推荐样本（同类型，不同公司）：**

1. [长江证券年报+一季报点评（太平洋证券）](http://pdf.dfcfw.com/pdf/H3_AP202605151822345754_1.pdf)
2. [财通证券年报+一季报点评](http://pdf.dfcfw.com/pdf/H3_AP202604301821801292_1.pdf)
3. [中信证券一季报点评（国信证券）](http://pdf.dfcfw.com/pdf/H3_AP202604261821587095_1.pdf)

### 提取字段（固定 `ExtractionResult`）

每个字段交给 LLM 提取。输入是管线产出的整份结构化 Markdown（正文 + HTML 表格 + LaTeX 公式 + VLM 图表描述合并在一起）。

单一真相源：`app/extractor/schemas.py` 的 `ExtractionResult`；前端 `frontend/src/types` 镜像同一形状。

| JSON 字段 | 类型 | 说明 |
|-----------|------|------|
| `company_name` | string | 公司名称（如「贵州茅台」） |
| `stock_code` | string | 证券代码（如「600519.SH」） |
| `report_period` | string | 报告期（如「2026Q1」） |
| `rating` | string | 投资评级（如「买入」「优于大市」） |
| `revenue` | `MetricPair` | 营业收入：`{value, change}` |
| `net_profit` | `MetricPair` | 归母净利润：`{value, change}` |
| `roe` | `MetricPair` | 加权平均 ROE：`{value, change}`（change 可空） |
| `total_assets` | `MetricPair` | 总资产：`{value, change}`（较年初） |
| `net_assets` | `MetricPair` | 归母净资产：`{value, change}` |
| `business_segments` | `BusinessSegment[]` | 业务板块数组：`{name, value, growth}`，行数不固定 |
| `profit_forecast` | `ProfitForecastRow[]` | 盈利预测（百万元）：默认 2026E/2027E/2028E，`{year, revenue, net_profit}` |
| `core_view` | string | 核心观点（一句话） |
| `risks` | string | 风险提示（分号分隔） |

缺省规则：字符串找不到填 `"无"`；`MetricPair.change` 找不到填 `""`；`business_segments` 无则 `[]`。

**不再提取（刻意不进模型）：** 研究机构/分析师、目标价、动态自定义字段。

### 固定输出模板（飞书 Card v2）

布局由 `app/feishu/table_formatter.py` + `card_builder.py` 硬编码，与前端 `FeishuCardPreview` 对齐：

```
【研报摘要】{company_name}({stock_code}) | {report_period}点评
评级: {rating}
─────────────────
核心财务指标 | 指标 / 数值 / 变动
  营业收入 / 归母净利润 / 加权平均 ROE
─────────────────
资产负债 | 指标 / 数值 / 变动
  总资产 / 归母净资产
─────────────────
业务板块表现 | 业务 / 收入规模 / 增速   ← business_segments 逐行
─────────────────
盈利预测(百万元) | 年份 / 营业收入 / 净利润
─────────────────
核心观点
风险提示
─────────────────
数据来源: {source_file}  |  提取时间: {extract_time}
```

### Agent 处理流程

```
上传 → 管线解析（MinerU → 分类 → 清洗 → 合并）
     → 整篇喂 LLM，按固定 ExtractionResult JSON Schema 提取
     → 待确认（前端编辑 + 卡片预览）→ confirm → 飞书发送（发送链路待接）
```

任务状态机：`queued → parsing → extracting → pending_confirm → sending → sent | failed`

## 三、模块设计

### 模块1：前端界面（`frontend/`）

**(1) 上传与任务详情**
- 上传：单文件 + 文件夹批量（`/upload`、批次页）
- 任务列表：状态筛选 / 搜索
- 详情页：轮询状态 → 固定字段编辑（`FieldEditor`，业务板块可增删行）→ Card 预览（`FeishuCardPreview`）→ 确认发送选群

**(2) ~~AI 提取字段配置~~（已取消）**
- 字段与卡片固定，不再提供 `/config/fields` 配置页

**(3) 群组目标设置**
- `/config/groups`：默认群 + 可选群、Webhook（已持久化）
- 权限映射：谁可发到哪些群（待做）

**(4) 执行与监控**
- 发送状态、失败重试、历史记录
- 建议记录「谁在何时确认/修改/发送了什么」（日志，不只是状态）

### 模块2：后端接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/upload` | 单文件上传，返回 `task_id` + `poll_url` |
| POST | `/upload/batch` | 批量上传，返回 `batch_id` + `task_ids` |
| GET | `/tasks` | 列表（`q` / `status` / `batch_id`） |
| GET | `/tasks/{id}` | 轮询任务状态 |
| GET | `/tasks/{id}/content` | 清洗后 Markdown |
| GET | `/tasks/{id}/result` | 固定 `ExtractionResult`（无 `field_config`） |
| GET | `/tasks/{id}/file` | 下载原始文件 |
| POST | `/tasks/{id}/confirm` | 提交完整 `fields` + `group_id` → 构建卡片并发送飞书 |
| GET | `/batches/{id}` | 批次进度 |
| PUT | `/config/groups` | 群聊目标配置（已持久化） |

**已删除：** `GET/PUT/POST /config/extraction-fields*`（字段不再可配置）。

### 模块3：Agent 核心逻辑

**管线部分（已实现）：**
```
main.py / PipelineService
  → app/cleaners/handlers/pdf.py
  → decomposer/（分类 + 清洗）
  → 合并为整份结构化 Markdown（ParsedDoc.content）
```

上传契约：前后端仅接受 `.pdf`（Word/HTML 已移除）。

**提取与卡片（已实现，固定契约）：**
```
结构化 Markdown
  → app/extractor/engine.py（DashScope，固定 prompt）
  → ExtractionResult.model_validate
  → app/feishu/card_builder.build_report_card（Card v2 table）
```

编排入口：`app/pipeline.py`（CLI）与 `app/services/pipeline_service.py`（API）。

**不向量检索、不切块的原因（来自 pineline.txt）：**
- 几十页内的文档整篇喂，不用 RAG
- 这一步只调用一次 LLM，是整个流程里唯一真正花钱的环节
- 前面的解析+清洗步骤已经让输入非常精炼：表格→HTML、公式→LaTeX、噪声已滤掉

**去重检测（待做）：** 同一家公司同一份研报可能被重复上传，建议在提取后、发送前用「公司名+研报标题+发布日期」做去重。

---

### 模块4：飞书接入

- 用飞书自定义机器人的 Webhook API 发送 Card v2
- 卡片构建已实现；`TaskService.confirm` 已同步发送 Webhook（可再接 Celery/限流）
- 注意事项：
  - 飞书群机器人有**发送频率限制**，批量发送时要做限流/排队
  - 消息体用卡片格式，不用纯文本

## 四、建议的数据模型

| 表 | 说明 |
|----|------|
| `tasks` | 任务：文件路径、`document_type=broker_report_review`、状态、时间、处理人 |
| `extraction_results` | 提取结果：关联 `task_id`，存固定 `ExtractionResult` JSON |
| `group_configs` | 群配置：群ID、名称、Webhook、默认/可选、权限范围 |
| `send_logs` | 发送日志：谁确认、何时发、发到哪群、AI 原始 vs 最终内容 |

**已取消：** `field_configs`（字段与 prompt/模板固定在代码里，不按用户配置）。

注：不做切块/向量检索；清洗后的 Markdown 可存在任务记录或文件系统。

运行时默认 SQLite（`data/app.db`）；Compose 可切 Postgres。
